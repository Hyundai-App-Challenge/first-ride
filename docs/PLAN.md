# QA 도구의 앱 대상 지정

로컬 debug 패키지를 별도로 설치해도 기존 release 데이터를 보존하며 같은 QA 도구로 검증한다.

## 성공 기준
- APP_ID로 지정한 앱의 신호원과 Activity만 변경·실행한다.
- 설치 실패 시 기존 앱을 삭제하지 않는다.
- 기본 패키지와 QA 패키지의 회귀 테스트가 통과한다.

## 범위와 순서
1. 대상 패키지·Activity를 공통으로 해석하고 세 스크립트에 적용한다(10분).
2. 자동 삭제를 없애고 실패·성공 경로를 테스트한다(10분).
3. 연결된 에뮬레이터에서 QA 패키지 신호 전환을 확인하고 PR·병합한다(10분).

앱 판정·화면·release 코스 범위는 변경하지 않는다. APP_ID를 생략하면 기존 com.firstride를 유지한다.

사용 스킬: plan·verify(완료 조건과 실행 증거), ponytail·karpathy-guidelines(기존 구조에 맞춘 최소 변경).


# W-50 STT 요청 격리

종료 이벤트 뒤 도착한 최종 텍스트가 다음 듣기를 완료하는 문제를 막는다.

## 성공 기준
- 종료 뒤 최종 텍스트는 같은 요청이 받고, 이전 요청의 늦은 콜백은 다음 요청을 완료하지 않는다.
- 실패·취소·시간 초과·동시 요청에도 SDK가 정리되고, 정리 완료 전 다음 SDK를 시작하지 않는다.
- 회귀 테스트와 실제 SDK 연속 요청·취소 검증을 통과한다.

순서: SDK 경계에서 콜백 순서를 재현(10분) → 요청별 소유·정리 구현(10분) → 실제 에뮬레이터와 전체 테스트 검증(10분).

앱의 STT 활성화와 세 어휘 실사용 정확도는 별도 게이트다. 공개 SttPort는 변경하지 않는다.

결정: 임의의 콜백 대기 시간을 두는 대신 요청마다 SDK를 만든다. 요청 ID가 없기 때문이며, SDK 경계만 가짜 인식기로 바꿔 늦은 콜백을 검증한다. 실제 연속 요청의 초기화→request는 이번 샘플에서 122/2/37ms였다(최초 차가운 연결은 약 1.3초). 추가 초기화 비용은 실사용 게이트에서 다시 확인한다.


# W-51 중단한 실습의 확인·재개

D→P 전환이나 백그라운드 복귀 후 실행기 없는 단계 화면에 머무는 문제를 해결한다.

## 성공 기준
- 주행 제한 중에는 재개 확인을 표시하지 않고, 정차·앱 복귀 때 사용자가 이어서 하기 또는 홈을 선택한다.
- 같은 단계에서 신호를 새로 확인하고, 이전 건너뜀은 시도 결과에 보존한다. 30분 초과는 홈으로 보낸다.
- 이전 음성·구독 정리 뒤 다음 실습을 시작하며, 앱 종료 후에는 재개 정보를 남기지 않는다.

순서: 기존 중단 경로·정책 확인 → 실행기 재개와 화면 연결 → 회귀 테스트·실제 SDK·낮/밤/큰 글씨 검증.

결정: 저장 형식·고정 포트는 바꾸지 않고 같은 실행기의 위치와 시도 집계만 메모리에 둔다. 새 화면은 현재 테마의 의미 색과 글꼴을 사용하고 88dp 버튼을 둔다. 동료의 테마·그림 파일은 수정하지 않는다. 사용 스킬: plan·verify, ponytail·karpathy-guidelines, ui-ux-pro-max.


# W-53 원상 복귀 안내의 SDK 미응답 제한

SDK 하나의 미응답 때문에 시작 전 값 수집과 완료 화면의 안내 전체가 대기하는 문제를 해결한다.

성공 기준: 시작 전 값은 병렬로 3초 안에 가능한 것만 모은다. 최초 관찰 미응답은 확인 못 함으로 표시하고 늦은 값은 반영한다. 취소 시 읽기·구독을 남기지 않으며 정상 신호가 오래 같아도 실패로 바꾸지 않는다.

순서: 미응답 회귀 테스트로 재현 → 기존 JudgeConfig/코루틴 채널로 제한 → 전체 테스트·실제 SDK 원상 복귀 검증. 새 설정 저장소·의존성은 추가하지 않는다. SignalSource와 reduce는 유지한다.

결정: 미응답 뒤 관찰을 끊는 대신 첫 값 대기만 제한한다. 사용자가 직접 되돌린 후의 갱신(AC-14-3)을 유지하기 위해서다. 사용 스킬: plan·verify, ponytail·karpathy-guidelines.


# W-55 소등 확인의 최초 신호 미응답

한 등의 첫 응답이 없을 때 소등 화면 전체가 로딩에 남는 문제를 해결한다.

성공 기준: 지원 여부는 동시에 확인하고 순서를 유지한다. 첫 신호는 기본 3초만 기다려 미응답을 UNKNOWN으로 표시한다. 늦은 실제 값과 변경은 계속 반영하고, 취소 시 구독을 정리한다.

순서: 기존 관찰 동작을 engine으로 옮겨 실패 재현 → 원상 복귀와 공유하는 내부 최초 응답 제한 적용 → 전체 테스트와 실제 SDK 소등 흐름 검증.

결정: 신호 포트·판정은 유지한다. 실제 두 호출자가 같은 제한을 필요로 하므로 기존 구현을 내부 함수로 이동해 중복 없이 사용한다. 표시·생명주기 UI는 기존 구조를 따른다. 사용 스킬: plan·verify, ponytail·karpathy-guidelines.


# W-57 시작 전 값 조회의 실습 범위

기준 값 조회가 별도 viewModelScope에서 실행돼 실습 취소 뒤에도 진행되고, 기준 확인 전에 단계 안내가 시작될 수 있는 문제를 해결한다.

성공 기준: 실행기가 기준 값을 먼저 확인하고 단계를 시작한다. 준비 취소는 조회도 정리한다. 재개는 원래 시도 기준을 유지하고, 새 시도는 기준을 다시 읽는다. 준비 취소로 기준이 없으면 미확인으로 두어 조작 후 값을 시작 전 값으로 오인하지 않는다.

순서: 실행기의 준비·취소·재개 조건 테스트 → 기준 소유권을 실행기에 이동하고 앱의 별도 async 제거 → 전체 테스트와 실제 SDK 재개·원상 복귀 확인.

결정: 같은 시도의 기준은 CourseRunner가 소유한다. 준비 완료 전 취소는 전체 기준을 미확인으로 둔다. 부분 결과를 별도 공유 상태로 관리하지 않아 동시 변경과 잘못된 재취득을 줄인다. 저장·신호 포트는 유지한다. 사용 스킬: plan·verify, ponytail·karpathy-guidelines.


# W-62 시작·홈 지원 확인의 화면 수명

백그라운드로 이동한 뒤에도 시작·홈 지원 확인이 남고, 숨은 화면의 D→P 이벤트가 시작 확인을 다시 켤 수 있는 문제를 해결한다.

성공 기준: 백그라운드에서 진행 중인 시작·홈 조회를 취소한다. 숨은 화면의 정차 복귀는 시작 확인을 실행하지 않는다. 화면 복귀 때 미완료 확인만 다시 실행하고 완료한 홈 결과는 유지한다. 기존 실습 재개·구성 변경 동작을 보존한다.

순서: 임시 지연 probe로 실제 생명주기의 대기 작업 재현 → 기존 Activity 콜백과 repeatOnLifecycle로 조회 범위 제한 → probe 제거 후 전체 빌드·실제 SDK·Activity 재생성 검증.

결정: 화면 복귀와 정차 복귀를 구분하는 private 상태만 둔다. 고정 포트·저장 형식·디자인 배치는 유지하며 새 의존성이나 테스트 프레임워크는 추가하지 않는다. 사용 스킬: plan·verify, ponytail·karpathy-guidelines.
